# AIForge task reservation and dependency contract

Status: proposed design for review. This document changes no API, storage, credential, client, or runtime behavior. Parent boundaries: [AIForge split](DESIGN-AIFORGE.md) and [verified identity/context](DESIGN-AIFORGE-CONTEXT.md). Updated: 2026-09-25. Source baseline: merged master `857f463`.

## Scope and authority

Aimem owns each project task, its history, and the single active reservation that guards work on it. Standalone agents and aicrew contend for that same reservation. Aicrew owns offers, attempts, workers, scheduling, messages, review and stop coordination; its attempt record is never a second task authority. This contract defines semantics for a future small integration API and fake consumer. Endpoint shapes, persistence schema, service authentication, migration, and release remain separate implementation reviews.

The protected legacy team path remains in force while both systems coexist. A new reservation cannot take a task currently managed by that path, and generic updates cannot bypass either protection. No existing managed-task row is converted, removed, or unprotected by this proposal.

## Identity and reservation record

Every agent-originated mutation is attributed to the stable aimem user ID authenticated by an individual credential; exceptional recovery records its separately authorized principal and the affected actor. The verified context selects exactly one grant source: personal grants or a team service access profile. A team role and session generation are independently checked through the [context contract](DESIGN-AIFORGE-CONTEXT.md). A bounded aicrew service call may carry a linked work reference, but service authentication alone cannot assert an arbitrary user or grant access to a project. The current actor, selected profile, hub ID and stable project ID must all agree with the verified binding. Display names are presentation only.

Conceptually, an active reservation contains the task ID, stable owning project ID, holder mode (standalone or external), authenticated actor ID, selected access profile ID, opaque holder/work reference, reservation ID, monotonic fence generation, task revision at its last transition, and lifecycle state. An external holder reference identifies an aicrew offer or attempt without storing aicrew's scheduling state in aimem. The holder reference is not a bearer token. A standalone holder has an individual work reference. Aicrew may reserve for an offer only through a verified coordinator context with a named intended worker and bounded offer reference; accepting the offer transfers the hold to the verified worker/attempt and advances the fence atomically. A declined or withdrawn offer releases under its current fence. A running attempt never inherits an offer timeout.

At most one active reservation exists per task, regardless of mode, actor, profile, or client. Reservation ID and fence are returned only to callers authorized for that task and their own hold. A new hold gets a new ID and a fence greater than every earlier generation for that task; release, transfer, stop and terminal transitions advance the fence before an old holder can write again. A task revision is a content/history compare-and-swap value, not an ownership fence: both values are required where a request can change task state. Reservation transitions and task/history/receipt changes commit atomically in the owning aimem task partition.

## Claim, write, release and finalize

| Operation | Required checks and effect |
| --- | --- |
| Claim | Reverify individual actor, selected context, live project grant and role; require an unarchived `READY` task at the expected revision and satisfy the project process's pickup gates; resolve dependencies as below; reject any active reservation or legacy managed protection. In one transaction create the hold, advance its fence, and record the receipt. Standalone pickup and an external offer/attempt use this same arbitration point. |
| Transfer to accepted work | Aicrew supplies its verified offer-to-attempt transition, expected task revision and current reservation ID/fence. Aimem confirms intended worker identity and current team context, updates the holder to that worker/attempt, and advances the fence in one transaction. A direct worker task call cannot make this transfer. |
| Work mutation | Require the authenticated holder, matching selected profile and current reservation ID/fence, expected task revision, permitted role and current grant. Recheck authorization before commit. No generic task write, admin path, or personal session may edit a held task through an unfenced route. Comments and evidence additions need a separate reviewed policy if they do not change task state; they must not become a state or ownership bypass. |
| Release | Require current holder or an explicitly authorized recovery principal, exact ID/fence and expected task revision. Record reason and outcome, advance the fence, then free the task in one transaction. A stopped or declined attempt returns to `READY`, or `BLOCKED` with a recorded blocker requiring explicit recovery; it never becomes `DONE` by release. Releasing accepted/running external work requires aicrew's confirmed stop or terminal reconciliation; a disconnect, heartbeat lapse, lost credential or role revocation is not proof of stop. |
| Finalize | Require current ID/fence, expected revision, authenticated actor/context or authorized recovery path, terminal outcome (`DONE` with reviewed delivery evidence, or `CANCELLED` with recorded reason) and project process gates. Commit terminal task state, history, receipt and reservation closure together. Aicrew's accepted result alone is not merge evidence or permission to mark DONE. No automatic merge, release or deployment follows. |

Every mutating request has a caller-generated idempotency key scoped to authenticated actor, operation and task/holder reference, plus a canonical input digest. An exact retry returns the original committed receipt without repeating the effect; reuse with different input is a conflict. The server rechecks present authorization before exposing a receipt. If the original actor loses access, a narrowly authorized recovery/status read can reconcile the operation without granting a new mutation. Receipt lookup reports committed, not committed or unresolved; unresolved must stop further writes until reconciled. A caller never responds to a lost reply by claiming again with a fresh key.

For a race between claim and a standalone update, exactly one transaction commits first. If the update wins, claim sees the changed revision and must re-evaluate. If claim wins, the generic update is refused as reserved even if its expected revision still matches. A stale fence cannot be repaired by merely reading the newer task revision. The same rule applies to archive, terminal state and any task write route. Task read and ordinary unreserved editing keep their existing access checks; dependencies remain advisory there.

## Dependency resolution

A dependency stores an immutable task ID; the owning project is resolved on the same aimem hub at evaluation time. The resolver uses the hub's authoritative task locator, then applies the caller's selected context and current read grant to the referenced project. It must not infer success from the shape of an ID, a cached task, a readable name, or an aicrew copy. A cross-hub ID has no verified state here and cannot satisfy a claim.

For claim eligibility, every listed dependency must resolve on this hub, be readable in the caller's active context, and have authoritative state `DONE` at the eligibility check. Archived `DONE` remains done; `CANCELLED`, missing, disabled, inaccessible and unresolved do not. The public response may combine missing and inaccessible into one non-disclosing `dependency_unresolved` reason; an authorized operator audit can retain the precise cause. The response names only dependencies the caller may read. Resolution errors and outages are retryable unknowns, never DONE. Duplicate IDs do not confer extra authority; a self-reference cannot be satisfied. A cycle remains ineligible until an authorized task edit resolves it, without an automatic graph scheduler.

Dependency evidence is checked again in the claim transaction or by a revision-pinned, same-hub snapshot whose validity the transaction proves. Cross-project storage partitions do not provide a single transaction today; the implementation must demonstrate an equivalent safe claim check before claiming atomic eligibility. If a dependency is reopened after a claim commits, the running reservation remains held and the change is surfaced for explicit reconciliation; it is not silently released or retroactively invalidated. Ordinary task creation, editing and dependency recording do not become blocked by incomplete dependencies under this contract. Pickup is the enforcement point, preserving the present advisory editing policy.

## Failure, revocation and project changes

The identity/context [failure envelope](DESIGN-AIFORGE-CONTEXT.md#failure-contract) applies to HTTP and MCP task operations: stable code, short explanation, safe active mode, retryable flag, one permitted next action and correlation ID. Exact wire spelling and status mapping belong to the later API review. Reservation-specific reasons include `reservation_conflict` (read current task and reconcile), `stale_fence` (stop the old holder and inspect current hold), `revision_conflict` (read current revision), `dependency_unresolved` (verify readable dependency evidence), `receipt_unresolved` (query receipt/recovery status), and `work_outstanding` (reconcile stop or result before leave). Refusals must not suggest switching to personal credentials or reveal another holder's private identity.

Revoking an aimem token, team membership, role, session generation or profile grant denies an operation whose authorization check starts afterward. The hold persists until the current owner or an authorized recovery principal proves stop/reconciliation. Rotation preserves stable actor identity but requires the context contract's fresh proof/rebind and a new generation; the old token/session/fence cannot continue new work. The two services do not share a transaction: authorization is revalidated immediately before each aimem commit, and an operation already authorized may finish as the context contract allows. Its committed result is recovered through its receipt rather than undone. An aimem stop transition advances the task fence atomically before a stale holder can write again; an aicrew role change alone cannot claim retroactive cancellation of an in-flight aimem operation. Lost connection never releases running work automatically.

Project rename resolves through stable project ID and current locator; a display name change cannot transfer a reservation. Disabling, deleting or moving a project with active holds requires an explicit administrative recovery/migration decision that preserves task history, receipts and fence monotonicity. Until that decision is committed, new claims and writes fail closed and existing holds remain visible to authorized recovery. A missing task, inaccessible project or removed grant must not turn an in-flight hold into an unowned writable task. No automatic cross-hub move is implied.

Terminal recovery is an auditable sequence: find the hold and receipt, establish whether execution is still active, request/confirm stop when needed, then either release to an eligible backlog state or finalize with the required reviewed delivery evidence. A revoked worker may be unable to submit; an authorized recovery principal can record the observed stop and close the hold, but cannot invent a completed result. Aicrew reconciles its attempt to the aimem receipt before offering replacement work. If either service is unavailable, preserve the hold and report an unresolved state.

## Fake-consumer proof before implementation

The first implementation task must use an isolated fake aicrew consumer against real aimem task routes/storage, then review the API fixture and version. At minimum it must prove:

1. Standalone and external claims racing for one task yield exactly one hold; generic update/archive and legacy managed-task bypass remain refused while protected.
2. Update versus claim, release versus late write, offer transfer versus old coordinator/worker write, and completion versus retry all obey revision and fence ordering.
3. Repeated identical keys return one effect and a stable receipt; changed input conflicts; lost reply, process restart and ambiguous commit reconcile without a second claim.
4. Team actor, profile, role, hub/project and session mismatch fail closed. Personal and team sessions remain isolated; revocation, downgrade and rotation fence writes while preserving running work for recovery.
5. Disconnect, aicrew outage and expired pre-work offer do not release accepted/running work. Stop acknowledgement, recovery release and DONE finalization each require their distinct evidence.
6. Same-hub dependency `DONE` in another readable project permits claim; `BACKLOG`, `CANCELLED`, reopened, missing, inaccessible, disabled and cross-hub evidence do not. Ordinary editing remains possible with incomplete dependencies.
7. Rename and project disable with a hold preserve ownership and history; unauthorized recovery, stale receipt and stale fence cannot claim or finalize the task.

The implementation should split into storage/transaction invariants, verified authorization and API fixtures, then client recovery/MCP behavior. Each slice needs its own READY assessment, exact-head tests and review. This contract is evidence for those tasks and for aicrew design; it does not approve a protocol implementation.

Current source basis at `857f463`: `internal/store/tasks.go` has task revisions, request receipts and syntax-only dependency validation; `internal/store/taskloc.go` locates task IDs across project partitions; `internal/server/tasks.go` authorizes current task writes by personal token grant; `internal/store/team_assignments.go` protects legacy managed tasks and checks dependencies for that path. None of these proves the proposed generic reservation, team profile authorization or cross-project atomic dependency check exists today.
