# AIForge clean-client enrollment wire contract, version 1

Status: reviewed contract (task D1-w, 01a10c7e-e0f5). D1-a serves issuance, revocation and listing (§1, §2) with the `aimem identity enroll` commands (§4, §5), over access schema 7. D1-b1 implements redemption in the ledger and the delivery sealing (§3, Delivery encryption, Bounds; `internal/access/enrollment_redeem.go`, `internal/enrollment`). D1-b2 serves the redemption route and `aimem enroll redeem` (§3, §5, Client protection), verified end to end; an installation enrolled this way skips journal push, as [What enrollment does not deliver](#what-enrollment-does-not-deliver) says. The contract fixtures live in `docs/fixtures/enrollment-v1/`: `examples.json` and the proposed OpenAPI, `openapi-proposal.json`.

This contract freezes the wire for the [enrollment contract](DESIGN-AIFORGE-ENROLLMENT.md) (D1): how an aimem operator issues an enrollment subcode, how a clean client redeems it for its individual credential, and how the credential reaches the client's installation without anyone else seeing it. It composes with the [identity wire](DESIGN-AIFORGE-IDENTITY-WIRE.md) (identity.v1), whose TLS, refusal envelope and request-key rules it reuses, and with aicrew's first-pilot text, [PILOT-1-FOLLOWUPS](https://github.com/BlackVS/aicrew/blob/6d97290/docs/proposals/PILOT-1-FOLLOWUPS.md) §3.9, §6.4 and §11, at aicrew `main` 6d97290. If a parent contract disagrees with this document, the parent wins, except for the corrections listed in [Corrections to the parent texts](#corrections-to-the-parent-texts).

## Operator decisions

The operator decided these points on 2026-10-05, recorded on task D1-w (comment seq272). They are design decisions, not implementation authorization.

1. **Redemption on the member's machine is an aimem command.** `aicrew-agent join` runs `aimem enroll redeem` and gives it the enrollment subcode record on standard input. aimem stores the bearer in the installation itself, and aicrew never sees the bearer.
2. **Delivery is encrypted with the standard library's HPKE** (`crypto/hpke`, RFC 9180), which needs Go 1.26. The toolchain moved to Go 1.26 first (#184).

The other choices in this text are proposals for review.

## Version, encoding and secrets

The protocol is `enrollment.v1`. HTTP carries the version in `X-Aimem-Enrollment-Version: 1`; a missing or unsupported version is `unsupported_version`, and nothing changes. enrollment.v1 is HTTP-only and has **no MCP tool**: every exchange carries a secret that must never enter a model-visible tool result. Bodies are UTF-8 JSON, IDs are stable opaque strings, and timestamps are RFC 3339 UTC.

| Secret | Format | Lifetime | Stored by |
| --- | --- | --- | --- |
| Enrollment subcode | `aes1_` followed by 43 base64url characters (256 random bits) | 24 h by default, at most 72 h | aimem, as a SHA-256 digest only |
| Delivery private key | X25519, 32 bytes, generated by `aimem enroll redeem` | Until the credential is stored, or the delivery copy expires | The client's installation, in the slot that will hold the bearer (see [Client protection](#client-protection)) |
| Individual bearer | The existing user-scoped token, `aimem_user_…` | 365 days from redemption (ordinary tokens allow at most 366) | aimem as a digest; the client in its installation |

The **bundle ID** is not a secret. It is a UUID that `aimem identity enroll issue` generates and that both services record for audit and revocation.

No response body, audit record, log line, task, fixture evidence or error message contains a subcode, a delivery private key or a bearer. A secret may appear only here:

| Secret | Permitted locations |
| --- | --- |
| Enrollment subcode | The `subcode` field of the issue response and of the subcode record; the `subcode` field of a redemption request |
| Delivery private key | The client's installation state, never on the wire |
| Individual bearer | Inside the encrypted delivery only; after decryption, the installation's credential slot |

## 1. Issue (operator → aimem)

`POST /v1/identity/enrollments`, hub admin only, over TLS the hub terminates (identity.v1's E3 rule). The admin token is the existing host-managed admin bearer. An aicrew peer credential, of any operation, cannot reach this route (`peer_forbidden`), and neither can an ordinary token (`credential_scope_forbidden`).

- **Request.** `{bundle_id, purpose, expires_at, user_name?}`.
  - `bundle_id` is a UUID the CLI generates, so that the operator knows it even when the reply is lost.
  - `purpose` is `new_user`. `existing_user_reissue` is reserved for D1-c and refused as `invalid_request` until D1-c defines its pins (stable user ID and old token ID).
  - `expires_at` must lie in the future and no more than 72 hours ahead.
  - `user_name` is the display name the new user will get. Without it, the hub uses the label the client gives at redemption. A name never selects a user (D1); it can be changed later with `aimem access user-set`.
- **Effect.** The hub stores `{bundle_id, purpose, subcode digest, expires_at, issued_by, user_name}` and the state `issued`. It stores no team, role or grant, because D1 gives the enrollment record none.
- **Answer.** `201` with `{bundle_id, purpose, expires_at, hub_id, subcode}`, sent with `Cache-Control: no-store`. The `hub_id` is the hub's stable identity (the access store's `hub_identity`), which identity.v1 already binds receipts to.
- **Lost reply.** The subcode cannot be recovered, because the hub keeps only its digest. Repeating the request with the same `bundle_id` and the same input answers `409` `enrollment_exists` without a subcode, and the operator revokes that bundle and issues a new one. A `bundle_id` reused with different input is `idempotency_conflict`.
- **Audit.** `enrollment.issued` with the bundle ID, purpose, expiry and admin, never the subcode.

## 2. Revoke and list (operator → aimem)

`POST /v1/identity/enrollments/{bundle_id}/revocation` and `GET /v1/identity/enrollments`, hub admin only, over hub TLS.

- **Revoke.** An unknown bundle ID is `not_found` (404). It succeeds for an `issued` bundle and makes it `revoked`. Revoking a `revoked` or `expired` bundle succeeds again and changes nothing. Revoking a `redeemed` bundle answers `409` `enrollment_redeemed`, with `{user_id, token_id}` of what it issued. D1: revoking a spent code does not revoke its token; the operator does that with `aimem access token-revoke` and `aimem access user-set … --state disabled`. Revocation and redemption are serialized in the store, and the one that commits first wins (D1).
- **List.** `{enrollments: [{bundle_id, purpose, state, created_at, expires_at, issued_by, user_name, redeemed: {user_id, token_id, at} | null}]}`, newest first, with an optional `?state=` filter. It never carries a subcode or a digest.
- **Audit.** `enrollment.revoked` and `enrollment.revoke.refused.redeemed`.

## 3. Redemption (client → aimem)

`POST /v1/identity/enrollments/redemptions`, over hub TLS only. **This route takes no bearer**: the subcode is the authority. An `Authorization` header is ignored, so a stale credential on the client cannot change the outcome.

- **Request key.** `Idempotency-Key` carries the client's random request key in identity.v1's `k1_` encoding. The client generates the key once per bundle and keeps it with the delivery key (see [Client protection](#client-protection)).
- **Request body.** `{hub_id, subcode, label, delivery: {suite, public_key}}`.
  - `hub_id` must be this hub's ID, as the subcode record carries it; otherwise `enrollment_invalid`.
  - `label` names the installation (1 to 64 characters from `[a-z0-9-]`): the token's label and, without an issuer-chosen `user_name`, the new user's name.
  - `suite` is `hpke-x25519-sha256-chacha20poly1305` (see [Delivery encryption](#delivery-encryption)); any other value is `invalid_request`.
  - `public_key` is the client's X25519 public key, 32 bytes in unpadded base64url.
- **Checks, in one store transaction.** The hub finds the subcode by digest and requires the bundle to be `issued`, unexpired and unrevoked. For a bundle that is already `redeemed`, it requires the same request key and the same input digest (`hub_id`, `label`, `suite`, `public_key`).
- **Effect of a first redemption.** In the same transaction the hub:
  - creates one user (enabled, no grants, no groups, no team profile, no admin role);
  - issues one user-scoped token for that user, expiring 365 days later (inside the store's 366-day limit for ordinary tokens), labeled `label`;
  - records the outcome under the bundle: the request key, the input digest, the user and token IDs and the encrypted delivery;
  - marks the bundle `redeemed`.
- **Answer.** `200` with `{bundle_id, replayed, hub_id, identity: {user_id, token_id}, delivery: {suite, enc, ciphertext}, redeemed_at}`, with `Cache-Control: no-store`.
- **Replay.** An identical retry (same subcode, request key and input) within the delivery retention returns the stored answer with `replayed: true`, also after the subcode's expiry: expiry stops a first redemption, not the replay of a committed one (D1). Before answering, the hub rechecks that the token still exists and is not revoked, and that the user is enabled (D1); otherwise it answers `enrollment_invalid`.
- **Conflict.** The same subcode with another request key, or the same key with other input, is `enrollment_conflict`. Concurrent first redemptions have exactly one winner; the others get `enrollment_conflict` when their key differs, or wait for the winner and replay when it is the same.
- **Non-disclosure.** Unknown, expired, revoked, already-redeemed-and-retention-expired and wrong-hub subcodes all answer the same `enrollment_invalid`. The audit keeps the exact reason (`enrollment.redeem.refused.<reason>`).
- **Audit.** `enrollment.redeemed` with the bundle, user, token and label; `enrollment.redeem.replayed`; never the subcode, the key or the ciphertext.

## Delivery encryption

The delivery uses HPKE (RFC 9180) in base mode with **DHKEM(X25519, HKDF-SHA256)**, **HKDF-SHA256** and **ChaCha20-Poly1305** (KEM `0x0020`, KDF `0x0001`, AEAD `0x0003`), as Go 1.26's `crypto/hpke` provides them. The suite name on the wire is `hpke-x25519-sha256-chacha20poly1305`; a later suite would need a new name, and the client refuses any name it does not know.

- **info** is the UTF-8 string `aimem enrollment.v1 delivery`.
- **aad** binds the ciphertext to its context. It is the UTF-8 string `enrollment.v1|<hub_id>|<bundle_id>|<request key, k1_ form>|<user_id>|<token_id>`.
- **Plaintext** is the JSON object `{"token": "aimem_user_…", "user_id": "…", "token_id": "…", "hub_id": "…"}`.
- **Answer fields.** `enc` is the encapsulated key and `ciphertext` the sealed plaintext, both unpadded base64url.

The client opens the ciphertext with its private key and the aad it rebuilds from the answer's IDs and its own request key. It then requires the plaintext's `user_id`, `token_id` and `hub_id` to equal the answer's and the subcode record's (`identity_mismatch` otherwise). A ciphertext that does not open is `identity_mismatch` too: the hub or the path is not the one the record named.

## 4. The subcode record

`aimem identity enroll issue --output -` writes one line of JSON to standard output and nothing else there. It is the unit that travels: aicrew's console reads it with `--bundle -`, puts it into the envelope unchanged, and `aicrew-agent join` hands it back to `aimem enroll redeem` on standard input.

```json
{"kind": "aimem-enrollment", "version": 1, "bundle_id": "…", "purpose": "new_user", "subcode": "aes1_…",
 "expires_at": "…", "hub": {"hub_id": "…", "url": "https://hub.example.test:8443", "trust": {"spki_sha256": "sha256-…"}}}
```

- **`hub.url`** is the hub URL the issuing CLI used (`--hub`), so it is a URL the operator verified.
- **`hub.trust`** is how the client verifies the hub, without trust on first use. It is the trust the issuing CLI itself used:
  - `{"spki_sha256": "sha256-<base64>"}` with `--hub-pin`;
  - `{"ca_pem": "-----BEGIN CERTIFICATE-----…"}` with `--hub-ca-file`, holding that file's certificates;
  - `{"system_roots": true}` with neither, for a hub whose certificate a public CA issued.
- **Size.** A record is at most 16,384 bytes; a larger one is refused by both tools.
- **No other secret.** The record carries the subcode and nothing else secret. In particular it carries no checkpoint token (see [What enrollment does not deliver](#what-enrollment-does-not-deliver)).

## 5. The commands

**`aimem identity enroll issue --purpose new-user --expires DURATION --output - [--user-name NAME]`** with the identity commands' hub flags (`--hub URL`, `--admin-token-file`, `--hub-ca-file` or `--hub-pin`).
- `--output -` is the only form, and it is refused when standard output is a terminal. There is no file form: D1 keeps subcodes out of files, so the record exists only in the pipe.
- `--expires` takes a Go duration up to `72h` (default `24h`).
- Every other line, including the bundle ID and the revoke command to run if the pipeline fails, goes to standard error.

**`aimem identity enroll revoke --bundle-id ID`** and **`aimem identity enroll list [--state STATE]`**, with the same hub flags. `--bundle-id` names the non-secret ID; `--bundle` stays the name of aicrew's flag for the record itself, so each flag has one meaning (one flag per intent, PILOT-1 §6).

**`aimem enroll redeem --hub-name NAME --label LABEL [--json]`**, on the member's machine, reading the subcode record on standard input. aicrew-agent runs it with the home's `AIMEM_STATE_DIR` and `AIMEM_SOCKET`.

1. It validates the record (kind, version, size) and reads the pending state for this bundle, if any. What follows depends on that state (see [Client protection](#client-protection)):
   - **No pending state: a first redemption.** It checks the record's expiry against the local clock. If the hub entry `NAME` already holds an individual credential that the hub accepts, it reports `already_enrolled` and exits 0 without sending the subcode, so a rerun of `join` never spends a second code (PILOT-1-FOLLOWUPS §11).
   - **Pending state in phase `sending`: a recovery.** A redemption may have committed whose reply was lost. The client does **not** check the subcode's expiry and goes to step 3 with the stored keys; the hub decides, because it replays a committed redemption for 1 hour after it, even past the subcode's expiry (D1).
   - **Pending state in phase `delivered`: the post-storage recovery.** The delivery was opened, and the bearer may already be stored. If the hub entry `NAME` holds a credential, the client verifies it with `GET /v1/access/identity` (step 6). When the hub reports the user and token recorded in the pending state, it deletes the pending state and reports `already_enrolled`, without contacting the redemption route, so this recovery never depends on the delivery retention. If no credential is stored, it replays the redemption as in the previous case.
   - A hub entry `NAME` that points to another hub URL is `identity_mismatch` in every case.
2. For a first redemption, it creates the pending state for this bundle in phase `sending`: the delivery key pair and the request key. Every later run reuses them, so a retry is the identical request the hub can replay.
3. It connects to `hub.url`, verifying the hub against `hub.trust` only; a hub that fails the check gets nothing.
4. It sends the redemption. A lost reply or a `5xx` is retried with the same key, up to 5 attempts with backoff. A first redemption retries only within the subcode's expiry; a recovery retries until the hub answers, and an answer of `enrollment_invalid` then means the retention has passed.
5. It opens the delivery and checks the identity. It then records the delivered `user_id` and `token_id` in the pending state and moves it to phase `delivered`, **before** it writes the hub entry `NAME` with `hub.url`, `hub.trust` and the bearer in the individual-credential slot (today's `task_token`, which `aimem hub credential` reports).
6. It verifies the stored credential with `GET /v1/access/identity` on the hub, requires the user and token the pending state recorded, then deletes the pending state.
7. It prints `{hub, user_id, token_id, bundle_id}` (with `--json`), never the bearer.

Exit codes follow the member reservation commands: `0` stored (or already enrolled), `3` final refusal (the code is printed), `4` retryable refusal, `5` outcome unknown (the pending state is kept; run the same command again), `2` usage.

## Client protection

D1 asks the client to protect the delivery key and the pending state in "client-supported OS credential storage" before it redeems. This contract places them **in the installation's own credential slot**: an owner-only file in the state root, created exclusively with mode 0600, or with a protected owner-only DACL on Windows, as hub.json, which holds the hub entries and their bearers, is written too. (Correction: until task 01a10fdd-f43a, hub.json was written with a file mode only, which on Windows sets no ACL, so it inherited its folder's access, observed on a development installation as a local group's read access. It is now written owner-only and atomically on every platform.)

The reason: the delivery key protects exactly one secret, the bearer, and the bearer is stored in that same slot moments later. Storing the key more strongly than the bearer it unlocks would add no protection. If the installation cannot create such a file, `aimem enroll redeem` refuses with `delivery_unavailable` before it sends anything, so no subcode is spent.

The pending state is `{bundle_id, phase, request_key, private_key, created_at, user_id?, token_id?}`. Each change is written atomically (write a new file, then rename it over the old one), so a crash leaves one phase or the other, never a mix:

| Phase | Written when | A rerun |
| --- | --- | --- |
| `sending` | before the first request is sent | replays the redemption with the same keys, even past the subcode's expiry |
| `delivered` | after the delivery opened and its identity checked, before the bearer is stored; it records `user_id` and `token_id` | verifies a stored credential against the recorded identity and finishes without the redemption route; replays only when no credential was stored |

The pending state is deleted once the stored credential is verified. It never holds the bearer.

## Refusals

Every refusal uses the context contract's envelope, `{code, message, retryable, next_action, correlation_id}`, as identity.v1 does. HTTP status is fixed by v1.

| Code | Status | Retryable | Where | Next action |
| --- | --- | --- | --- | --- |
| `invalid_request`, `unsupported_version` | 400 | no | hub | Correct the request or use a supported version. |
| `tls_required` | 403 | no | hub | Connect to the hub's TLS listener with certificate verification. |
| `credential_scope_forbidden`, `peer_forbidden` | 403 | no | hub, admin routes | Use the hub admin credential. |
| `enrollment_invalid` | 403 | no | hub, redemption | Ask the operator for a new onboarding code. |
| `enrollment_conflict` | 409 | no | hub, redemption | Do not retry with another key; ask the operator, who checks the bundle's audit. |
| `enrollment_exists` | 409 | no | hub, issue | Revoke the bundle and issue a new one; its subcode cannot be shown again. |
| `enrollment_redeemed` | 409 | no | hub, revoke | Revoke the issued token and disable the user if the redemption was not legitimate. |
| `not_found` | 404 | no | hub, revoke | Check the bundle ID with `aimem identity enroll list`. |
| `idempotency_conflict` | 409 | no | hub, issue | Use a new bundle ID for other input. |
| `rate_limited` | 429 | yes | hub | Wait, then try again with the same key. |
| `enrollment_unavailable` | 503 | yes | hub | Retry with the same key; nothing was applied. |
| `identity_mismatch` | — | no | client | Stop: the hub, the record or the installation disagree. The operator checks the bundle. |
| `delivery_unavailable` | — | no | client | Fix the installation's state directory; nothing was sent. |

## Bounds

The limits below are values fixed by this contract. An implementation may tighten them; relaxing any of them needs a reviewed v2.

- A subcode lives 24 h by default and at most 72 h (D1).
- A redemption's encrypted delivery is kept for **1 hour** after the first redemption, whether or not the subcode has expired since. Within that window an identical retry replays it; after it, a retry is `enrollment_invalid`, and the operator recovers as D1 describes (revoke the issued token, issue a new bundle). A client that already stored its credential does not need the window (phase `delivered`).
- Redemption is limited to **10 requests per minute per client address** and **20 per minute per bundle**. The subcode's 256 bits make guessing infeasible, so the limits bound load, not guessing.
- An issued token expires 365 days after redemption, inside the existing 366-day limit for ordinary tokens.
- A subcode record is at most 16,384 bytes; a redemption request body at most 4,096 bytes.
- The client makes at most 5 redemption attempts per run, each bounded to 10 s.

## What enrollment does not deliver

- **The checkpoint token.** A hub's journal push uses the shared checkpoint token, and a user-scoped token cannot push (the hub keeps the legacy writer surface from ordinary tokens). D1's envelope carries only the two subcodes, so an enrolled installation has the individual credential for proofs, team mode, tasks and the pilot's knowledge reads, but no journal push. Giving it push access is a separate decision: a user-scoped push permission on the hub, or the checkpoint token by another channel. It is outside D1.
- **Grants, groups and team profiles.** The new user has none. Team access comes from the team profile's grants, after aicrew links the agent through identity.v1's proof.
- **Existing-user reissue.** D1-c defines it on top of this wire.

## Corrections to the parent texts

- **D1, protected storage.** "Client-supported OS credential storage" becomes the installation's own credential slot, for the reason in [Client protection](#client-protection).
- **D1, the one change the first pilot needs.** The composed onboarding envelope may be written by aicrew's console client to an owner-only file on the operator's machine for the private hand-off, and the operator deletes it after sending (PILOT-1 §7). The member side is unchanged, and no subcode file exists.
- **aicrew's pipeline (PILOT-1-FOLLOWUPS §3.9).** `aimem identity enroll issue --hub <hub id>` becomes `--hub <hub URL>`, as in every identity command: the hub ID comes back from the hub itself and goes into the record. The revoke command aicrew's console prints becomes `aimem identity enroll revoke --bundle-id <id>`.

## Delivery

- **D1-a** implements §1, §2, §4 and `enroll issue|revoke|list`, with access-schema 7 for the enrollment ledger. The redemption route is not served yet: D1 allows no public redemption until the complete path is verified.
- **D1-b** implements §3, the delivery encryption, `aimem enroll redeem` and the client protection, and serves the redemption route.
- **D1-c** adds `existing_user_reissue`.
