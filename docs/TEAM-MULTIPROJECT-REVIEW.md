# Review: portable teams and multi-project coordination

Final. Staged direction approved by the owner on 2026-09-23. Reviewed source: e3dea35aa7e63f2ad01d072ea71f3e74a459292e (v0.7.2), including the regenerated command assets. The increment 1 contract is [portable team context and honest readiness](DESIGN-portable-team-context.md) (task 01a0cf0f-d158-7000-8956-40d43405d5fe); where it corrects this review, the contract governs and the corrections are listed there and under "Instruction delivery" below. Later increments keep their own design and review gates. No migration or live-team changes are part of this review.

The current design is coherent for a team working within one project, but it cannot represent a user-level team spanning several projects. Adopt portable instruction delivery first, then separate team membership from project execution while preserving atomic assignment and recovery guarantees.

Implementation risk: **HIGH** for the multi-project refactor because it changes authorization, durable ownership and migration boundaries; **MEDIUM** for instruction delivery alone. These are proposed extensions to the explicitly single-project v1 contract, not grounds to reopen already merged PRs.

**Scope and evidence**

The README calls aimem “Session resilience and shared memory for AI coding agents.” The current implementation additionally owns durable task coordination: enrollment, sessions, offers, ownership, results and audit. This review covers those boundaries, local MCP onboarding and instruction delivery, not the curator, embedding pipeline or a new autonomous supervisor. The requested target is one team on one hub, with agents on different hosts and clients, some started outside a repository, working across explicitly associated projects. Cross-hub federation is deferred. “Subproject” initially means an existing aimem project, not a new inherited permission hierarchy.

Inputs are operator-owned enrollment/project grants, ordinary scoped tokens, client-declared platform/model information, agent commands carrying generations and retry keys, Git-owned instructions/process references, and local checkout identity. The hub owns the wire protocol and durable state; projects own their task/process policy; clients own local execution. Missing authority must refuse an operation, missing context must prevent dependent work, and unknown model/capability declarations remain unknown.

Outputs are durable task/session/message records, immutable results and audit, onboarding reports, generated client commands, process context and release binaries. Consumers include the local CLI and stdio MCP facade, Claude/Codex/OpenCode command assets, hub task APIs/UI, and an eventual supervisor. No external project checkout was inspected; this review derives portability limits from the shared contracts and source, not assumed downstream behavior.

| Artifact | Producer | Consumers | Contract | Failure if broken |
| --- | --- | --- | --- | --- |
| Team and enrollment | Operator and project DB | Session API | Team belongs to a stable project instance | Same team cannot serve another project |
| Ordinary credential | Access service and local credential store | Task/team HTTP callers | Current grants intersect token scope; no fallback from a required local token | Denial, or authority widening if a refactor bypasses it |
| Saved membership | Shared setup core | CLI and local MCP | Canonical checkout, hub, project and token binding | Changing checkout loses the continuation context |
| Assignment and reservation | Project transaction | Coordinator, worker and task API | Task state, worker capacity, receipts and audit commit together | Duplicate work or stranded ownership if split across stores naively |
| Playbook | Git document | Generated commands and agents | Current instructions name a repository-relative file | An arbitrary project checkout has no such file |
| Process set | Git source, hub-selected commit, local cache | Bootstrap and onboarding | Exact reference and complete manifest assets | Missing context is reported; selection is not proof of agent receipt |
| Client command assets | Embedded templates in release binary | Three agent clients | Generated instructions match installed binary | Old commands keep invoking the old onboarding path |

Concrete flow: `internal/wiring/assets/join_team.md` is embedded by `internal/wiring/commands.go:15`, compiled by `.github/workflows/release.yml:53`, and installed by `aimem teams commands`. The client invokes `team_setup`; `internal/mcp/onboard.go:42` constructs an environment bound to the MCP process's checkout, and `internal/teamsetup/teamsetup.go:299` checks that binding before joining. The resulting role instruction sends the agent to `docs/TEAM-PLAYBOOKS.md` (`internal/wiring/assets/join_team.md:60`; setup lines 884/891). The binary carries the command template, but this path does not deliver the referenced playbook. Regeneration and client restart are manual deployment steps. The relative document path is an implicit consumer contract; abbreviated behavioral instructions are also duplicated in templates and server responses.

**Findings, ordered by consequence**

1. **Structural — project is both authorization boundary and team container [CONFIRMED-SOURCE, FOLLOW_UP].** `docs/DESIGN-agent-teams.md:108` explicitly selects one project. `internal/store/teams.go:33` stores ProjectInstance, `internal/server/team_sessions.go:59` requires ordinary project write authority, and `internal/mcp/teams.go:187` constructs project-prefixed routes. Passing a different project argument selects another project's teams; it does not make one membership multi-project. Boundary: team directory versus project work. Smallest increment: define a hub-scoped team identity, explicit project associations and authorization matrix before changing routes. Preserve v1 clients as single-project clients.

2. **Critical before multi-project execution — atomicity is presently project-local [CONFIRMED-SOURCE, FOLLOW_UP].** `internal/store/store.go:964` links assignments to local tasks and sessions and enforces one reserved attempt per task and worker. `internal/store/team_assignments.go:142` validates and saves the offer under one project transaction, including the busy-worker check. Cloning sessions into multiple project databases would allow each database to see an idle worker; moving only sessions to a separate database removes the current transaction boundary. This is a refactoring hazard, not a demonstrated collision in supported v1 usage. Boundary: task mutation, worker reservation, fencing, inbox event and receipt. First increment: a storage ADR and migration prototype that proves these still commit or roll back together.

3. **Structural — checkout identifies the continuing agent [CONFIRMED-SOURCE, FOLLOW_UP].** `internal/teamstate/teamstate.go:22` binds state to Repo/Project/HubURL/TokenID, and line 58 hashes only the checkout into the state filename. `internal/mcp/onboard.go:31` fixes the environment at MCP startup; setup line 299 resolves it before any membership action. This intentionally supports one saved context per checkout but cannot express an independent agent switching projects or two explicitly separate instances in the same directory. Boundary: agent/session identity versus execution workspace. First increment: a named user-level agent context with explicit instance/session selection; retain checkout binding only for execution and project credentials.

4. **Operational — joining does not prove instruction or execution readiness [CONFIRMED-SOURCE; live symptom reported by owner, FOLLOW_UP].** The playbook path above is not a delivered artifact. `internal/teamsetup/teamsetup.go:110` reports session/check data without the full playbook; `checkProcess` at line 570 warns rather than blocks, and uses the selected set mainly to check required skills. The owner reported successful join/heartbeat followed by inability to read the playbook because the shell failed. A source review establishes the missing delivery contract; no new live join was performed. Boundary: membership versus permission to begin work. First increment: deliver the role instructions through MCP with version/digest and a separate context-ready report, tested in a repository that is not aimem with shell execution unavailable.

5. **Structural — project-scoped visibility currently protects team-wide messages [CONFIRMED-SOURCE, FOLLOW_UP].** Session access requires project write authority (`internal/server/team_sessions.go:59`), while `internal/mcp/teams.go:64` explicitly describes all messages as team-visible. Once members have different project grants, copying that visibility rule would disclose project content. `internal/server/team_assignments.go:14` already checks the worker's live token and target project grant; retain and extend that contract. Boundary: team-common information versus project data. First increment: specify scopes for messages, references, results, audit and inbox delivery, including revocation and coordinator visibility, before exposing a multi-project API.

Existing safeguards worth retaining: explicit enrollment, server-derived identity, token binding, session and coordinator generations, strict local credential selection, idempotent retries, immutable results, durable inbox acknowledgements and transactional reservation constraints. A missing heartbeat does not release ownership (`internal/store/team_sessions.go:54`). No new allocator, identity provider, message broker or terminal-control system is justified by this review.

**Proposed model**

| Concept | Owner and lifetime | Relationship |
| --- | --- | --- |
| Principal | Existing hub access service | User/service identity with live project grants |
| Agent context | User configuration, independent of cwd | Named configuration selects hub and ordinary credential source; no secret in repository configuration |
| Agent instance/session | Hub registration, local saved nonsecret handle | Distinguishes concurrent clients even with the same principal/token; explicit resume preserves fencing |
| Team | Hub coordination service | Enrollment, roles, one coordinator, common instructions and explicit allowed project instances |
| Project | Existing project identity | Tasks, grants, repository/process policy and its own integration gates |
| Attempt | Hub work transaction | Explicit project instance, task, team, member session/generation and frozen requirements |
| Execution binding | Member's local host | Attempt mapped to an approved local checkout/worktree, repo identity and base commit |

One team spans several projects on the same hub. A coordinator can join without a repository and communicate from any host. A coding worker still needs local repository/tool access before accepting execution. A planning-only coordinator need not prove a compiler exists; independent source review needs its own suitable workspace and access.

A user-level token follows its live grants, as today. A project-scoped token remains capped to that project and cannot silently use a user token for wider access. The effective task authority is the intersection of team project association, member enrollment, role, token scope and live project grant. Team association grants no project permission. A multi-project coordinator needs access to the projects it coordinates; absent access is explicit, not a partially successful global view. A project-token member can receive common team context and its permitted project work only. Define team-common content as visible to every enrolled member; project messages require an explicit scope and authorization on each read, including replay, inbox delivery and audit. Revocation prevents future reads; it cannot erase content already received.

Start with one active task reservation per agent instance across all its team memberships on the hub, not per principal: two deliberately separate agents may share a user. Resume advances generations; copying saved state to another host is not a supported takeover. Local credential protection remains OS-specific, and credentials are installed separately on each host.

Do not add an arbitrary `cwd` or filesystem-path parameter to the owner-context MCP tool. User-level coordination uses a fixed agent configuration; project execution binds through an explicit locally configured workspace handle. It must not turn the credential-owning MCP process into a general shell or filesystem proxy. Changing cwd is not authorization to change credentials or access another project.

**Instruction delivery**

Keep Git as the authoring authority and do not turn a mutable shared note into workflow policy. Two kinds of content need delivery, and they have different owners. The team protocol guidance (the playbook and its request templates) is public, versioned with the protocol and already validated against the storage code of the same release; it ships embedded in the aimem binary, like the command templates, and both MCP facades serve it by stable section id with a version and digest. The binding team rules are already part of the project's selected process handbook; the process set, its admin selection and its exact-commit cache (`internal/process/process.go:31`, `:82`) are reused unchanged, and setup/continue deliver the same bootstrap unit the session-start hook injects. This removes the need to clone the aimem repository or run a shell to read instructions.

Corrections made by the contract, with their evidence: no separate team instruction selection in v1, because a team lives in exactly one project and a second selection would create a second policy authority; the hub-published bundle is needed only for project process content on hosts without Git access to the process repository, and is optional; the current assignment record snapshots requirements and profile but no instruction versions, so workers declare them in evidence until a schema change records them. Use a small versioned resource contract, not a generic remote file browser. Tool names such as `team_context` and `process_context` are proposals, not existing APIs. Never silently truncate required content: size limits are enforced when the binary is built. Missing or incompatible content yields a visible not-ready state and an `unavailable` worker heartbeat, which the hub's existing offer and accept checks already honor, while preserving an already-created membership. A policy update cannot silently rewrite an accepted attempt's requirements. Security revocation remains live.

A published project shared document could temporarily improve reachability, but current `list_docs`/`read_doc` are project/group scoped and do not establish this team-wide immutable contract. Do not add a hand-maintained copy in each project.

**Storage decision**

| Option | Benefit | Cost or limit | Recommendation |
| --- | --- | --- | --- |
| Keep project teams; improve context delivery | Smallest change, preserves all transactions | No unified multi-project membership or capacity | First useful increment; honest single-project pilot |
| Hub team directory plus project-local task transactions | Avoids moving task records initially | Requires durable cross-store reservation, reconciliation and event delivery; no atomic commit across ordinary independent WAL databases | Avoid as the default design; acceptable only if moving storage proves substantially worse |
| One hub work database for task and coordination records | One transaction for task revision, capacity, generations, inbox, receipt and audit across projects | Significant one-time migration and backup/API work; shared writer throughput must be measured | Preferred target if true multi-project teams are accepted |

The preferred target is a separate work database, not moving journals, memories and every other project feature into one database. Existing access.db remains the identity authority. Project IDs/instances stay on all project records, and project API routes continue to filter and authorize them. Move task comments/history/receipts/epics/management records and required process references along with tasks where they participate in transactional contracts; inventory that closure before implementing. Do not declare the migration small from table count alone.

Prototype and measure before selecting the final schema: concurrent offers from different projects must reserve an instance once; failure injection must roll back state/event/receipt together. Compare expected write load with one SQLite writer. No migration should be deployed merely to unblock reading a playbook.

**Delivery proposal — five increments**

1. **Portable role context and honest readiness (split into 1a contract, 1b embedded role context, 1c readiness in setup/continue, optional 1d hub-served process bundle; see the contract).** Deliver playbook content through MCP and update join/resume templates. Keep existing project teams. Prove delivery in a non-aimem checkout with no shell and from a second host; missing/truncated/stale context blocks work, not an unnecessary second join. Do not claim this fixes the Codex runner.
2. **User-level agent context (M slices after design approval).** Add explicit hub/context selection and named instance state independent of cwd; preserve checkout mode and strict project-token behavior. Initially it can coordinate a selected existing project team. Prove repeat/resume, two instances sharing a credential, wrong-hub refusal and no arbitrary path access.
3. **Work-store ADR and migration prototype (L: split investigation from implementation).** Inventory all transactional records, prototype the preferred single work store and run collision/crash/backup tests. Keep production v1 untouched until the evidence and migration plan are reviewed. No dual writable authorities.
4. **Multi-project protocol and migration (L/XL: separate storage, authorization and client increments).** Add explicit team project associations, per-operation project identity, visibility checks and hub-wide capacity. Preserve old routes as single-project adapters; refuse unsupported wider operations instead of silently choosing the cwd. Migrate one backed-up, stopped hub at a time, preserve IDs/history/receipts and compare counts/invariants. Preserve existing single-project team name resolution; ambiguous hub-wide names require qualification or ID, never automatic merging. Active attempts must be quiesced before migration; sessions require a documented reconnect/fencing plan. A post-write downgrade requires explicit data recovery, not just restoring the old executable.
5. **Cross-host pilot (bounded S/M scenarios).** Coordinator outside a repository, workers in two authorized projects, third worker intermittently offline, mixed project/user tokens, restart while busy, revoked grant, denied cross-project message, duplicate offers, failed execution setup and audit export. Verify Windows/Linux/macOS separately; unavailable platforms remain pending. Preserve human merge and each project's integration serialization.

**Verification and known limitations**

This is a source architecture review, not a tested implementation proposal. Inspected tests cover assignment races/rollback (`internal/store/team_assignments_test.go:264`, `:380`), credential and checkout refusal (`internal/mcp/onboard_test.go:236`) and absent onboarding tools on the hub facade (`:312`). Those tests support v1 boundaries; they do not prove multi-project behavior or actual client readiness. No tests were rerun because no production code changed. The separate Codex shell failure prevents a complete native coding pilot and remains unresolved.

PR99/100 removed duplicated setup logic and moved credential use into the local MCP owner process; they addressed credential-account execution, not portable instruction distribution or hub-scoped teams. Generated assets still require explicit refresh and client restart. The roadmap baseline is corrected to v0.7.2 in the same change as the increment 1 contract; live state remains on the board. The separation of durable coordination from optional host supervision in [the supervisor design](DESIGN-agent-supervisor.md) remains applicable.

Recommendations: approve increment 1 first; use it for the single-project pilot while validating the broader model. Approve user-level context as a separate boundary. Choose the work-store migration only after its prototype validates atomicity and migration cost. Keep project authority and message visibility explicit throughout. Defer cross-hub teams and automatic host supervision.
