# AIForge clean-client enrollment contract

Status: D1 design candidate for review; the authorization choices in [Operator decisions](#operator-decisions) are approved on task D1. No enrollment operation is implemented by this document.

This contract extends the [AIForge identity and context contract](DESIGN-AIFORGE-CONTEXT.md) for a new installation that has no individual aimem credential. It composes with the aicrew [onboarding contract at 36f07f0](https://github.com/BlackVS/aicrew/blob/36f07f058fb45493c8607a5f465e8a5657a5a5f0/docs/ONBOARDING-CONTRACT.md), which already defines invitation, proof, link and session behavior. That commit is on the locally tracked aicrew `main` and `origin/main`; the remote was unavailable to a read-only lookup during D1 assessment. If aicrew changes its contract before implementation, reconcile the new head explicitly. The merged aimem context contract remains authority for actor authentication, grants, proof and session context.

## Outcome and trust boundary

An operator authorizes one onboarding bundle and privately gives the person at a clean client **one onboarding code**. The person runs **one client bootstrap command** and enters the code at a hidden prompt. The client obtains exactly one persistent, individual, user-scoped aimem credential for that installation directly from aimem, stores it in protected local state, and then uses aicrew's existing invitation and aimem proof flow to link or join. The operator transfers a short-lived code, never a credential file or proof receipt. Aicrew receives only its invitation subcode and a one-time aimem proof receipt; it never receives the enrollment subcode, individual bearer or protected storage contents.

The onboarding code is a client-unpacked envelope with two independent bearer capabilities: an **aimem enrollment subcode** issued by aimem under aimem operator authority, and an **aicrew invitation subcode** issued by aicrew under its operator authority. The envelope also carries nonsecret hub/service locators and authenticated endpoint identity bindings, stable hub ID, bundle ID and a version/checksum. It is one artifact entered once; the client does not submit the whole envelope to either service. Aicrew's invitation issuance, digest-only storage, team/role/hub scope, begin/complete semantics and refusal codes remain as already contracted. The envelope is not a third credential and confers no additional authority. A shared bearer sent to both services is outside this contract.

The operator's issuance workflow may call both services, but neither service trusts the other's operator authentication. Aimem independently verifies an operator with explicit enrollment authority for the target hub and operation; aicrew independently verifies an operator with invitation authority for the target team and role. Aicrew's service credential cannot issue or redeem an aimem enrollment capability, create an aimem user or mint an aimem token. Neither ordinary team coordinators nor an invitation alone have aimem enrollment authority. Issuance fails closed if either operator authorization is absent.

## Scope and issuance

The operator chooses a stable hub ID and aicrew service/team/role, a `join` or `link` invitation, and any required agent binding. D1 enrollment does not compose with a `rebind` invitation, which changes an existing agent's verified user and needs its separate aicrew work reconciliation. The two records share a random bundle ID for audit and client-side scope comparison; this does not create a cross-service transaction. The aimem record contains purpose `new_user` or `existing_user_reissue`, issuing operator, target hub, pinned user ID and old installation token ID for reissue, maximum credential scope, expiry, revocation state, attempt controls and digest of its random subcode. It contains no team grant and no authority to choose a different hub, user or old token at redemption. The aicrew invitation remains scoped under its contract. The operator sees both short-lived subcodes only while composing the envelope and sends the resulting one-time code through a private channel. Neither subcode, envelope nor receipt goes in command arguments, environment variables, files used for ordinary config, Git, logs, tasks or chat.

The aimem subcode has at least 128 bits of cryptographic randomness, is stored by digest, is redeemable once, expires by default after 24 hours and never after more than 72 hours. The bundle is usable only until the earlier component expiry. The operator can revoke either unredeemed component; to cancel the bundle, the operator revokes both, with audit of partial failure. Issuance should not reveal the envelope until both services acknowledge their scoped records. If one issuance succeeds and the other fails before reveal, the workflow revokes the first and reports incomplete; a retry uses a new bundle ID and new capabilities. The two issuances and revocations are not falsely described as atomic.

For a **new identity**, aimem creates one new stable user ID and one user-scoped installation credential in the same redemption transaction. It creates no direct personal grants, access-group memberships, team profile grants, admin role or project token. The aicrew invitation may initially have no user pin because the user ID does not exist at issuance; its verified proof receipt must identify the newly created hub/user, and the client must check the hub and scope against the envelope before completing. A new identity joining a team gains only whatever live team-profile grants are independently configured and verified later; an invitation itself grants no aimem resource access.

An installation that **already has a working credential** uses the existing aicrew invitation/proof flow; it does not need a D1 enrollment bundle or mint a second credential. For an **existing identity on a clean installation without its credential**, aimem enrollment is an explicit recovery/reissue operation pinned to the stable hub/user ID and the old installation token ID by an aimem operator with reissue authority. The operator obtains that token ID from aimem's authenticated inventory; if the specific installation token cannot be identified unambiguously, this flow stops for an operator decision. It never revokes every credential for the user by default. Names, labels, repository paths, invitation claims and aicrew service assertions cannot select the user or token. Aimem checks that the old token belongs to the pinned hub/user and issues one new installation token for the same user while revoking that exact old token in the same aimem transaction. Other tokens are untouched. Active team sessions and work are reconciled under the context contract. Revocation denies operations whose authorization check starts after it commits; it does not retroactively cancel an already authorized operation. Because the new token can use that user's existing personal grants, this is privileged account recovery, not a routine team invitation. It requires a separate audit and operator confirmation of the target identity and rotation impact. A user who needs another independent agent identity receives a new aimem user instead; the aicrew contract maps one aimem user to one aicrew agent.

An operator must not issue an aimem capability for an existing user merely because aicrew presents a linked agent ID or a role. Aicrew invitation `rebind` is a separate, operator-authorized identity-link change and does not silently trigger credential reissue. The aicrew user pin is mandatory for existing-user recovery and must match the aimem enrollment record; otherwise the client refuses before invitation completion.

## Client redemption and protected delivery

1. The bootstrap command reads the envelope through a hidden prompt, validates its format and expiry, checks the expected stable hub/service IDs over authenticated transports, and keeps both subcodes only in process memory. The operator's private code handoff supplies the endpoint identity binding; a locator alone or silent trust-on-first-use is insufficient. The client verifies each service against the encoded trust binding (such as a CA-backed DNS identity or pinned public key) before sending its subcode. No fallback to a broader credential is allowed.
2. Before redemption, the client creates a fresh delivery key pair and request key, and durably protects the private key and pending bundle state in client-supported OS credential storage. It sends the aimem subcode, request key and public delivery key directly to aimem. The aicrew subcode is not sent at this step.
3. Aimem verifies its own operator-issued record, hub/user binding, expiry, revocation and attempt policy. It atomically consumes the capability, creates or reissues the stable user/token as scoped, records the idempotent outcome and a bounded encrypted delivery copy addressed only to the supplied client public key. It returns the same encrypted result for an identical retry with the same request key and delivery key. Conflicting reuse is refused. The aimem bearer is never returned in plaintext to aicrew or persisted in an operator artifact. A second client racing with another request cannot obtain a second credential from the same capability.
4. The client authenticates and decrypts the aimem response locally, stores the credential in the protected installation slot, and verifies the resulting stable hub/user/token identity directly with aimem. Only after successful durable storage does it discard the enrollment subcode and begin the aicrew invitation flow. The final installation has one active aimem credential; no general config file, repository, environment variable or command history holds it.
5. The client sends only the aicrew invitation subcode to aicrew `begin`; then it sends the challenge with its individual aimem credential directly to aimem for a one-time proof receipt; then it sends the invitation subcode, challenge and receipt to aicrew `complete`. Aicrew's existing proof, idempotency, invitation state, role and session rules apply unchanged. The client compares the verified hub/user and invitation team/role/pin to the authorized bundle scope before accepting success.

The exact cryptographic suite, credential-store integration, route schemas, transport authentication, retention and timeout values are implementation-review work. The binding requirements above are contract requirements; a plaintext response, loggable bearer, caller-selected actor or permissive verifier does not satisfy them. If the client cannot protect the private key or credential, it refuses enrollment before consuming the code.

## Retries, expiry and recovery

An aimem enrollment redemption is single-effect and idempotent for the same request key and delivery key. Aimem records the outcome and encrypted response atomically with token creation or rotation. A lost HTTP reply is retried with the same key and retained client private key, returning the same result while the bounded delivery record remains available. Expiry prevents a new redemption, but a previously committed identical retry may recover within that retention period. After retention expires or the client loses its protected delivery key, aimem will not disclose or mint a replacement from the spent code; the operator revokes any issued token as appropriate and starts a new, audited recovery. An ambiguous client must first query/replay its recorded request and never assume a timeout means no token was issued.

Revocation before aimem consumption wins the race and denies redemption. Consumption before revocation yields one issued token; revoking the spent code alone does not revoke that token, so the operator must explicitly revoke the credential to undo issuance. Aimem serializes these transitions and audits the winner. Concurrent redemption with different keys produces one winner and generic refusal for the others. The client treats unknown, expired, revoked, consumed and locked codes as one non-disclosing enrollment refusal, with an operator audit reason; transient service unavailability is retryable with the same key. Failed validation never creates a user/token. Replays must recheck that the issued token still exists and has not been revoked before delivering its encrypted copy.

Aicrew begin/complete retries, challenge expiry, invitation attempt limits, revocation and receipt recovery remain exactly as its onboarding contract specifies. If aimem issuance succeeds but aicrew is unavailable or linking fails, the client keeps the protected aimem credential and first retries the existing invitation as long as its state, deadline and attempt budget allow. It obtains a fresh invitation pinned to the same user only when the existing one can no longer be used. It never re-enrolls solely to recover an aicrew failure. If aicrew link succeeds but the client loses its completion reply, the client retries with the same completion key or re-proves the linked identity as the aicrew contract allows. If aicrew membership is later removed, that does not silently revoke the aimem credential; aimem token revocation is a separate authorized action.

The operator sees each service's audit state by bundle ID and follows a partial-failure runbook: no code revealed -> revoke prepared records; code revealed but no aimem redemption -> revoke both and reissue if needed; aimem redeemed but no aicrew link -> retain/recover the credential, retry the existing invitation while usable, and issue a fresh pinned invitation only if needed; aicrew linked -> reconcile membership/session and aimem credential separately. A crash in either service cannot turn an unconfirmed response into a second identity, token or membership. No cross-service rollback is promised.

## Failure and access rules

The client gets a stable code, short explanation, retryable flag, permitted next action and correlation ID in the context contract's failure envelope. Public enrollment refusals do not disclose whether an existing user, invitation or code exists. `enrollment_invalid` covers invalid, expired, revoked, consumed or locked aimem codes; `enrollment_conflict` covers conflicting request-key or delivery-key reuse; `delivery_unavailable` indicates protected local storage cannot be established; `enrollment_unavailable` is retryable service failure; `identity_mismatch` covers verified hub/user/scope disagreement. Exact HTTP/MCP spelling and status mapping require an implementation/OpenAPI review. No response or audit visible to ordinary callers contains a bearer, enrollment subcode, private delivery key or another actor's identity.

Enrollment proves only authorized credential issuance. It does not prove aicrew membership, selected team context, role, resource grant or reservation ownership. After enrollment, every aimem request still authenticates the individual token and selected context; team operations still require current aicrew introspection and aimem profile grants. A new user with no direct grants gains no personal project access merely by completing enrollment. Existing-user reissue deliberately restores that user's existing direct grants, which is why its authority is separate and explicit.

## Operator decisions

Task D1 comment seq148 presented these choices. The operator approved all three in comments seq153-155 and clarified the second and third in seq157. These are design decisions, not implementation authorization:

1. **Approved:** one client-visible code is a client-unpacked envelope of independently issued capabilities. The aicrew invitation remains aicrew-issued and sees no unspent aimem enrollment subcode. A shared bearer would change the aicrew contract and expose aimem issuance authority to the invitation service.
2. **Approved:** clean-install recovery of an existing identity requires aimem operator reissue authority, stable user pin and revocation/fencing of only the specifically identified installation token. If the token is ambiguous, an operator decides how to proceed. Allowing overlapping credentials would need a separate reviewed policy.
3. **Approved:** an aimem credential already delivered to protected client state survives later aicrew invitation failure. The client retries the existing invitation while usable, then obtains a fresh invitation for the same verified user only if needed, without a second aimem enrollment.

The implementation review must also set exact bounds for aimem attempts, response retention and client trust/bootstrap of endpoint identities. It may choose wire encodings and a standard authenticated encryption suite without relaxing the authority, atomicity, single-use or separation requirements above.

## Delivery split and dependency order

| Increment | Owner | Verifiable outcome |
| --- | --- | --- |
| Aimem issuance and ledger | aimem enrollment child | Operator authorization distinct from aicrew service; scoped digest-only records, expiry/revocation, audited state, concurrent redemption and additive migration tested internally. No public redemption until the complete path is verified. |
| Aimem credential redemption | aimem enrollment child | Atomic user/token/receipt outcome, client-key-bound encrypted delivery, replay/revocation/rotation and crash recovery tests; exact route and OpenAPI reviewed together. |
| Aimem proof and context | E2-E5 | Individual credential proof, peer verification, selected context and grant enforcement; no trusted request fields or permissive production verifier. D1 must be settled before E2 freezes proof/credential wire. |
| Operator bundle workflow | aimem/aicrew integration children | Both issuers independently authorize; one code is shown only after both scoped components exist; partial issuance/revocation recovery and audit are tested. Aicrew's existing invitation contract is preserved. |
| Client bootstrap | aicrew client child | One command and hidden code entry; split capabilities locally, verify both service scopes, store one aimem credential securely, then use existing invitation/proof flow. Tests cover lost replies, expired/revoked components and fresh/existing identity. |

No row is an implementation authorization from D1 alone. The final clean-client path requires reviewed aimem enrollment and aicrew bootstrap together. E1 remains internal substrate; C5/C6 reservation authorization and public routes are separate and still deferred. This design changes no live credential, service configuration or deployment.
