## Authority and version boundary

`reservation.v1` is a proposed, opt-in integration surface. The selected personal or team context is bound to the authenticated connection, never selected by a request field. Aimem derives the actor from the individual credential; it checks current grant, role, session generation, task ownership and fence before a transition and again immediately before commit. A bounded aicrew service request is accepted only with a separately verified transition for the same linked actor, team, task, work reference, operation and generation. The service credential alone cannot impersonate an actor. C5 must implement and prove these checks before C6 registers any route or tool. Until then every proposed operation is unavailable.

The proposed OpenAPI intentionally leaves its security scheme unset: C5 has not selected credential transport for bounded service calls or operator recovery. Its `x-security-gate` marks this as a required completion condition, not as a public or unauthenticated route. C6 must add the reviewed schemes and operation policies before embedding the spec. Aicrew never receives an individual's aimem bearer.

The protocol version is carried as `X-Aimem-Reservation-Version: 1` for HTTP and `version: 1` in MCP tool input. Missing or unsupported versions fail `unsupported_version` without a mutation. A future version needs its own reviewed fixture; a server must not silently reinterpret v1. Identifiers are stable hub/project/task/actor IDs, never names or URLs. The path project ID is checked against aimem's current task locator; rename does not change identity. Cross-hub, disabled, moved, missing or inaccessible project evidence fails closed.

The proposed HTTP paths are under `/v1/projects/{project_id}/tasks/{task_id}/reservation`: `POST /{operation}` for `claim`, `transfer`, `update`, `release`, `finalize`; `GET` on the base path for authorized current status; and `GET /receipts/{operation}/{request_key}` for reconciliation. MCP proposes matching `task_reservation_<operation>`, `task_reservation_status`, and `task_reservation_receipt` tools. HTTP and MCP use the same JSON request/result/error bodies and authorization rules. MCP returns a typed refusal with the same `code`, `retryable`, `next_action` and `correlation_id`; transport errors are not a substitute for a committed receipt. These names and paths are frozen for v1 consumers by this design, but remain unregistered until C6.

## Canonical request

Every mutation has an opaque caller-generated `request_key` (HTTP `Idempotency-Key`, MCP input field) and a canonical digest over operation, path task ID, version and all JSON body fields. A request key is scoped to authenticated actor, operation and task; the holder reference is **inside the digest**, so changing it under the same key is a conflict rather than a second namespace. The server records the transition and its receipt in one owner-task transaction. Identical replay returns the recorded result after current disclosure authorization; changed input under that key returns `idempotency_conflict`. Key retention is durable for the life of the task's reservation history; C6 must specify any later pruning separately, without permitting key reuse. The request must not include an actor ID, grant list, role, token, session handle or arbitrary selected profile. The verifier supplies that binding from the connection and trusted aicrew introspection. A service transition carries only its bounded `coordination_proof` reference, not a bearer or actor assertion.

All mutations carry positive `expected_revision`. `transfer`, `update`, `release`, and `finalize` also carry `reservation_id` and positive `fence` as a decimal string. Fence strings avoid JSON integer precision loss. `claim` supplies a holder `{mode, work_ref}`: `standalone` with the individual's work reference in personal context, or `external` with aicrew's immutable offer/attempt reference in team context. The server verifies the reference against current coordination facts; the opaque reference itself grants no authority. Transfer replaces an external offer holder with the named worker's external attempt and advances the fence. Its proof must bind the exact offer, intended worker, accepted attempt and current generation; the worker cannot self-transfer by direct task call.

`update` carries complete task content and a transition intent such as `block`, `submit`, or `resume`; it does not create a second task API or bypass existing task validation. It is available only to the authenticated current holder under current context. `release` carries complete task content for `READY` or `BLOCKED`, a reason, and stop/nonacceptance evidence appropriate to its stage. `finalize` carries complete terminal task content (`DONE` or `CANCELLED`), a reason and `terminal_evidence`. `DONE` requires reviewed delivery and human-merge evidence under the selected project process; acceptance of an aicrew result is insufficient. The receipt and resulting outcome together record the server-derived actor and verified mode, resulting task revision, reservation ID/fence, effect and immutable coordination reference. The response discloses only the caller's own authorized hold; another holder's identity or work reference is never returned.

### Approved actor rules

| Stage and operation | Permitted verified principal | Required proof and refusal behavior |
| --- | --- | --- |
| Offer claim | Active coordinator's individual team context through the bounded service transition | Named intended worker, immutable offer reference, current team/project/profile grant and coordinator generation. |
| Offer transfer | Bounded aicrew transition tied to accepted offer and intended worker's verified team context | Same offer/attempt, exact reservation ID/fence/revision and current worker generation. A direct worker call cannot transfer. |
| Declined, withdrawn or expired unaccepted offer release | Current verified coordinator; after handoff a verified successor coordinator; otherwise separately authorized operator recovery principal | Durable aicrew fact that the offer was never accepted, exact hold and fence, and no competing accepted/running attempt. Declining worker records aicrew decline but does not release the coordinator hold. Timer/disconnect alone and ambiguous verification preserve the hold and capacity. |
| Worker-held update or stop release | Current worker holder in its verified team context; separately authorized recovery only after confirmed stop | Coordinator review does not permit impersonating a worker or releasing running work. Lost session, credential or connection is not stop evidence. |
| Worker-held finalize | Current worker holder **or** current reviewing coordinator under a narrow terminal operation; separately authorized audited recovery if neither can act | Coordinator must have its own verified individual actor, active team role/session/generation, project grant, and fresh aicrew confirmation that this exact attempt is accepted for finalization. Exact fence/revision and terminal evidence are mandatory. This is not holder write or arbitrary service authority. Competing calls resolve by one CAS/receipt. |
| Independent worker claim and subsequent work | The independent worker's verified team context | `external` holder referencing its own aicrew attempt, with aicrew capacity/intent receipt. It is never a personal `standalone` hold or a coordinator offer. |

Operator recovery is a distinct auditable path, not an implicit admin-token override. Its concrete authentication and proof verification belong to C5. A blocked, revoked or unreachable participant cannot be replaced by an arbitrary service call. Receipt/status reads recheck current authority; when the original actor loses access, only the narrow authorized recovery reader can reconcile without granting a new mutation.

## Response, reconciliation and refusal

A committed mutation returns HTTP `200` with `receipt.state: committed`, the unchanged `request_key`, operation, server-derived attribution, resulting task revision and current or closed reservation. A closed reservation has an empty active ID and no holder reference, while its advanced fence remains durable; the request key and receipt reconcile the transition that closed it. An identical retry returns the recorded outcome and receipt ID without repeating the effect; only the transport hint `replayed` changes to `true`. Claim conflict or another final refusal has no receipt unless an earlier identical request committed. A lost reply is resolved with the receipt endpoint using the original operation/key and original authorization context; `not_committed` means the caller may retry the same key, while `unresolved` means stop all later transitions until reconciliation. A retry with a fresh key is never the recovery instruction. A status read returns only the caller's authorized hold summary or `none`; it is not a substitute for receipt lookup after an ambiguous call.

Every refusal has `{code, message, active_mode, retryable, next_action, correlation_id}`. `active_mode` is omitted when disclosing it is unsafe. `message` is short and nonsecret; `next_action` is one permitted instruction, never a suggestion to switch to personal credentials. No denial reveals another holder's actor, session, team, work reference, token, proof or private dependency. `dependency_unresolved` may name only dependencies currently readable in the selected context. HTTP status mappings in the proposed OpenAPI are part of v1: malformed input `400`, missing/revoked credential `401`, verified role/grant refusal `403`, hidden/missing task or dependency `404` only where non-disclosure requires it, revision/fence/reservation/idempotency conflicts `409`, unavailable verification or unresolved outcome `503`, unsupported version `400`. MCP carries the same stable code regardless of its transport status. Clients classify by code and `retryable`, not status alone.

| Code | Retryable | Permitted next action |
| --- | --- | --- |
| `invalid_credential` | no | Recover the individual credential through its authorized flow. |
| `identity_link_required`, `identity_mismatch`, `context_missing`, `context_stale` | no | Re-prove or resume the team context and reconcile outstanding work. |
| `context_unavailable` | yes | Retry verification later with the same context and key. |
| `grant_denied`, `role_forbidden` | no | Request authorized access or use the permitted aicrew flow. |
| `task_unavailable` | no | Verify the task reference with an authorized project reader. |
| `dependency_unresolved` | yes only for verified transient outage; otherwise no | Verify readable dependency evidence before a same-key retry. |
| `reservation_conflict`, `revision_conflict`, `stale_fence` | no | Read own authorized status and reconcile; stale holder stops. |
| `idempotency_conflict` | no | Investigate changed input; never replace the original key to force a transition. |
| `receipt_unresolved` | yes | Reconcile the original receipt; do not send a later transition. |
| `work_outstanding` | no | Reconcile accepted or stopped work before leaving or rotating. |
| `unsupported_version`, `invalid_request` | no | Use a reviewed supported version or correct the request. |

After an operation begins authorization, concurrent revocation follows the merged in-flight context rule: C5 revalidates immediately before commit; a transition already authorized may complete, with its receipt used for reconciliation. A late dependency reopen after claim commit is surfaced through C3 reconciliation without silent release. No response claims a multi-database transaction.

## Fixture gate and deferred implementation
